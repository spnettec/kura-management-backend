# Center ordinary-profile handoff v1

The bound center can explicitly hand an already approved recovery completion to the gateway's pre-provisioned ordinary Kura profile. This builds on the agent's [fixed ordinary handoff](../../kura-management-agent/docs/ordinary-profile-handoff-v1.md). It neither installs a distribution nor enables boot, restarts/reboots a gateway, or certifies every Kura business component.

The agent must have a reviewed private `AGENT_RECOVERY_ORDINARY_STARTUP_CONFIG`, its existing recovery grants, and explicit `AGENT_RECOVERY_ORDINARY_REMOTE=1` (default `0`). Only then does it advertise `recovery.ordinary.v1`. The ordinary JVM never waits for the agent and does not carry a recovery request. Remote management's existing persistent OFF decision still controls the center connection independently.

Additive protocol-major 1 operations 20–22:

| Operation | Request | Authority and outcome |
| --- | --- | --- |
| `recovery.ordinary.status` (20) | no action | Admin-only read of current handoff eligibility/state, approved completion identity and ordinary status. No parent or handoff token is returned. Only this operation is read-retryable. |
| `recovery.ordinary.prepare` (21) | no action | Selects only the current locally committed completion, validates its immutable evidence and fixed ordinary grant, and prepares a new short-lived `handoff-UUID`. It does not start Kura. |
| `recovery.ordinary.execute` (22) | `ordinaryHandoffAction: {transactionId, confirmationToken}` | Requires the exact prepared handoff UUID and canonical confirmation UUID. Rechecks the original profile/source, durably records the issued intent, stops the old recovery units and starts the fixed ordinary unit once. |

The caller cannot supply a unit, executable, path, snapshot, parent completion, profile, provider list or expected business value. A prepared plan exposes its fixed unit/profile, reviewed digests, approved source snapshot digest, component/check lists and confirmation deadline for explicit review. Tokens stay in existing encrypted task input/results; viewer/operator task responses redact the prepare token. Browser storage contains only intent/idempotency keys and original task IDs, never confirmation tokens.

All three HTTP operations require admin, CSRF, current gateway ownership/enabled state and a fresh advertised capability. Dispatch independently checks the capability and binding generation. Writes share the existing online write lock and native system-change coordinator. Only the exact current RUNNING durable admission, with matching full protobuf hash, operation and idempotency key, can be excluded from the recovery pending-write check. Other RUNNING/UNKNOWN writes still block it; local recovery callers do not gain that exclusion.

A long handoff may cross the transport lease and become UNKNOWN. The browser continues bounded GET reads of that original task, without resending or preparing a replacement. A lost HTTP acknowledgement preserves an uncertain intent across reload and blocks new handoffs. The admin-only read `GET /api/v1/gateways/{id}/task-intents/{key}` can recover the original ID after a lost HTTP acknowledgement. It is scoped to the same actor, tenant, gateway and idempotency key; another administrator cannot claim that intent. A 404 keeps the uncertainty gate because the original admission may still be in flight. An existing durable execution receipt can settle the original task after expiry/reconnect. A native decision alone is not a receipt bound to the original remote command: process loss before receipt persistence remains UNKNOWN for these operations. It must not be inferred successful from the current unit or from a later historical decision. A dedicated native handoff command resolver remains pending.

Native recovery's issued-intent/immutable-receipt rules are unchanged: interruption cannot automatically start again; missing or inconsistent evidence requires recovery, preserves the scene, and blocks writes. The center independently rejects success overclaims and an execute receipt naming another handoff. Successful execution is `ORDINARY_ACTIVE_APPROVED_CHECKS`, `scope=administrator-selected-checks`, `ordinaryUnitHandedOff=true`, `normalBootVerified=false`, `kuraRecoveryVerified=false` with a schema-2 ready observation. Snapshot hash echo is context, not proof of actual file loading. The reviewed live providers establish their selected business assertions.

Migration `0017_ordinary_handoff_tasks.sql` extends only the operation check; prior migrations/wire numbers remain unchanged. Restart/reboot lifecycle, full Core installation/upgrade and all-component/reboot business verification remain separate pending work.
