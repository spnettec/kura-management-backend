# 中心证书和信任配置的界面生效（V52 增量）

2026-11-14；实现仍在同一 R013 shadow，未整体应用到原仓库、未提交推送。方案 A 的外部 CA 和私钥保管方式不变；本功能不接收 CA 私钥。

## 操作

管理员在设置页选择服务器证书/私钥及客户端 CA 的 PEM 文件，核对指纹并分别暂存，再到“证书与信任配置生效”核对本批两项指纹和网关数后生效。未更改的一项沿用当前配置。HTTPS 与 gRPC/mTLS 一起选择新一代配置，旧握手和长连接关闭；浏览器、agent 按新证书和信任重新建立连接。必须提前准备客户端所需的信任证书。CA 的更换不代替网关证书签发/轮换。

该流程不要求用户设置环境变量、运行生效脚本或手工重启中心。初次软件安装、首次配置向导、独立 agent 配置与续期、备份恢复和批量运维仍按完整台账继续，不能据此宣称部署全流程完成。任务密钥恢复仍是现有独立的重启生效流程。

## 一代配置和重启

`tls-runtime-active.json` 是唯一联合选择点，引用现有不可变 TLS/CA generation，不覆盖只读 bootstrap 文件。所有材料有完整摘要约束；服务器证书校验私钥匹配、有效期及中心 origin 的主机名，CA 校验保持原合同。两个服务的 TLS 配置均在发布意图前构造完成，由同一运行时读锁取得对应配置和连接 epoch。gRPC 连接携带实际握手的 peer identity 与 epoch，epoch 失效会取消原流的工作，不能在旧信任连接上继续领取任务。

首次升级只采用旧 active 或 bootstrap，保留 pending；启动/重启不再自动批准 pending。已有联合指针时只采用该指针，旧 active 元数据作为历史保留。旧式散落 pending 文件仍要求明确审查。state 目录有进程级独占租约，拒绝第二个进程共享同一份证书运行状态。

## 原操作和故障

界面先持久保存 operationId、已核对的 active generation 与 pending revision，再发一次 POST。服务器先认证管理员并验证 CSRF，记录 REQUESTED 审计，再写原意图、发布联合指针、交换内存配置，最后记录回执并关闭旧连接。文件为当前用户私有、拒绝 symlink，采用不可覆盖的原意图/回执和 fsync/原子发布；旧代和失败文件保留。

`GET /api/v1/settings/tls-activation` 返回当前/待生效指纹和 server-side blockingOperationId；POST 带 operationId/expectedGeneration/pendingRevision；`GET .../tls-activation/{id}` 只读原记录。三种原结果：APPLIED 有原回执；REJECTED 有执行前拒绝记录且无生效意图，必须重新核对；UNKNOWN 缺失/无效/发布未核定的回执。observedActive 只是当前进程正在使用该精确联合 manifest 的观察，不补造回执。联合指针发布不确定时停止网关通道，保留 HTTPS 供认证查询。

回执丢失、连接断开、404 都不授权重发。重复 POST 相同 ID 只是观察；改变相同 ID 的请求被拒绝。原 UNKNOWN 从服务端阻止后续暂存和生效，另一个管理员或浏览器也不能用新 ID 绕过。新浏览器会从服务端恢复原 ID 并只查询；未实现的人工核定/恢复界面仍属内部 pending，不能伪造 APPLIED 或偷偷清除原记录。
