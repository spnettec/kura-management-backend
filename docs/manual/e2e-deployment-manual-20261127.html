第二步：证书体系

证书作用谁持有私钥
client-ca签发各网关的 leaf 证书；中心和网关用它验证对端部署者（宿主 E2E_ROOT/pki）
server-ca签发中心服务端证书；网关用它锚定中心部署者
server.pem / server.key中心的 HTTPS 与 gRPC 服务端证书管理中心
gw-<网关>-leaf.pem网关的身份证书，只能做客户端用途（CA:FALSE）各网关（私钥不出网关）
  • SAN 必须覆盖浏览器与两类虚拟机访问中心的全部地址
  • 证书在 OpenSSL 容器里生成与签发，避免 macOS LibreSSL 的显式参数编码
bash 02-ca.sh
# subjectAltName = DNS:localhost, DNS:host.orb.internal, IP:127.0.0.1, IP:198.18.0.1, IP:10.211.55.2

如果浏览器不用 localhost 访问中心，把 CONSOLE_NAME 设成那个名字（脚本会自动加进 SAN），或者用 CONSOLE_EXTRA_SAN 追加。网关 leaf 的扩展是固定的：basicConstraints CA:FALSE、keyUsage digitalSignature、extendedKeyUsage clientAuth、SKI、AKI。

备注：02-ca.sh 生成三份证书；05-gateway-enroll.sh 为每台网关签发 leaf。

控制器里的各类拒绝都是防丢失的保护，在干净系统上按上面的顺序执行不会出现。常见的几种：对已初始化的 agent 换一个新的 UUID 再 initialize 会报 “Retain the original native initialization UUID”；已有 peer 授权时再次 authorize 会报 “Existing control-group authority requires its original migration”；手工删过 agent 的状态目录后会留下空的 legacy 目录，再装包会报 “Retained legacy profile requires explicit original migration”。遇到这些，不要继续在这台机器上试，按第六步还原到基线重来。

第五步：网关登记（顺序固定）

  1. keygen：网关自己生成密钥和 CSR私钥不出网关；GW_ID 写进 CSR 的 CN
  2. 中心侧用 client CA 签发 leafpki-sign-leaf.sh，在 OpenSSL 容器里签
  3. 注册：POST /api/v1/gateways必做。未注册的网关即使 bind 成功，中心也会拒绝连接（FORBIDDEN）
  4. stage：生成登记槽位gw-stage-final.py，端点必须带 https:// 前缀
  5. enroll：kurad register + bind → 启用通道 → 启动 kura → CONNECTEDbind 之前先停 kura 释放桥的登记位

第六步：第四台网关用 Parallels 快照还原

  1. 停机prlctl stop。带内存的快照在停机状态下还原最干净
  2. 还原：prlctl snapshot-switch --id <快照> --skip-resume回到未安装任何 Kura 组件的基线
  3. 启动并核验基线vm-baseline.sh：0 个 kura 包、没有 /opt/eclipse/kura、没有 agent 状态目录
  4. 文件经宿主 httpd 送入prlctl exec 按空格重切参数，只能传单个命令；脚本一律 curl 后本地执行
prlctl stop "YOFC Review ARM64 20261124"
prlctl snapshot-switch "YOFC Review ARM64 20261124" --id "{ce60c087-5614-477b-92d1-8c003317d150}" --skip-resume
prlctl start "YOFC Review ARM64 20261124"

实测结论：对这台虚拟机做 snapshot-switch，内存和磁盘会一起回到快照时刻（boot_id 变成快照时刻的、uptime 回到快照时的秒数、/tmp 与 /run 这两个 tmpfs 里的内容也一起还原）。上一轮的密钥、登记材料和存活进程不会残留。流程仍然固定为先停机、还原、再冷启动，并在启动后跑一遍基线核验。

3 号文本终端用来显示步骤、供截图。实测：chvt 返回时 getty@tty3 已经 active（systemd-logind 对还没人用的终端会按需起 getty），之后 40 次采样写入全部成功。但 getty 启动那一刻会对终端做 vhangup 并打印登录横幅，紧接着 chvt 的写入会以 EIO 失败、已写的内容被横幅顶掉。所以 vm-install.sh 在切换后等 getty@tty3 处于 active、再停 1 秒才清屏：截图里只有步骤行，日志里没有写入错误。

发现并修复的产品缺陷

+ let spawn_deadline = Instant::now() + Duration::from_secs(5);
+ let mut child = loop {
+     match command.spawn() {
+         Err(error) if error.raw_os_error() == Some(libc::ETXTBSY)
+             && Instant::now() < spawn_deadline => {
+             std::thread::sleep(Duration::from_millis(5));
+         }
+         spawned => break spawned?,
+     }
+ };

kura-management-agent  src/process.rs  3a713f5
  • 现象：全量并发测试偶发失败，报错都是 Text file busy (os error 26)；修复前 5 轮里 4 轮出现，每轮 1–2 项，共落在 5 个不同的测试上
  • 位置：agent 启动子进程的 spawn()；内核在目标程序仍被以写方式打开时拒绝 exec
  • 推断的机制：别的线程在 fork 与 exec 之间带着继承来的写句柄
  • 修复：遇到 ETXTBSY 等待后重试，上限 5 秒
  • 验证：修复后全量并发 5 轮，每轮 808 项通过、0 项失败

发现过程：从清空的编译缓存重新编译后，agent 自己的测试套件全量并发执行 807 项，1 项失败，调用栈停在对一个 Err 的 unwrap 上。

nm::handover::startup::tests::legacy_bound_source_drives_original_stop_and_stopped_file_publication_without_java_report
Text file busy (os error 26)

对照实验用同一个容器、同一份 cargo 缓存和同样的参数。修复前：把修复提交之前的源码（f11d66f）导出，全量并发跑 5 轮，其中 4 轮出现偶发失败（各轮偶发失败数依次为 1、1、2、0、1），涉及 5 个不同的测试，报错完全相同。 再把修复提交里新增的回归测试原样加进修复前的源码，只跑它这一项：结果 FAILED，失败在同一个错误上（Text file busy (os error 26)）。 修复后：同一套测试全量并发跑 5 轮，共 4040 项通过、0 项失败。

内核在可执行文件还被某个进程以写方式打开时拒绝 execve。能同时解释“只在并发时出现”“每次是不同测试”的机制是：durable::write 写完临时文件后先改名、写句柄要到函数末尾才关；这个线程之外，别的线程恰好在 fork()，子进程继承了这份写句柄的副本，直到它自己 exec 时才关闭；原线程如果抢在这之前执行这个脚本，就得到 ETXTBSY。这个机制是从内核语义和实验现象推出来的，没有用系统调用跟踪逐次证实。修复不依赖这个推断：无论是谁短暂地持有写句柄，等它放开再执行都是正确行为。

agent 运行期是 tokio 多线程的，同样会 fork 子进程，所以这不只是测试不稳，是一个概率极低但真实存在的生产竞态。修复提交新增的回归测试让另一个线程持有脚本的写句柄 400 毫秒后放开，同时执行这个脚本。

过程中撤回的两个结论

当时的说法错在哪实际情况
Ubuntu 上 bind 的 INVALID_ARGUMENT 是平台问题，需要改 agent 源码没有先查知识库，也没有确认带诊断输出的 agent 是否真的装上了同一台虚拟机、同样的 Ubuntu，按已验证的顺序一次通过。原因在做法：对运行中的虚拟机还原、登记目录里有旧材料、没有先注册
prlctl snapshot-switch 对运行中的虚拟机“延迟生效”，内存不随磁盘还原凭一次前后不一致的现象下了因果结论实验表明内存与磁盘一起、立即还原到快照时刻

另外三件做错的事，一并记下：一是没有先查工作空间知识库就自己另写了一套 Core 构建驱动，接连踩了 git archive 没有 .git、容器 umask 002 让 49 个 JAR 变成组可写、编译树与打包树的 target 不同步三个坑，改用仓库自带的 build-all.sh 后一次编过；二是把 agent 的 cargo test 放进了 noexec 的 /tmp 且去掉了全部 capability，得到一堆假失败；三是合并 kura 时用 checkout --ours 解决冲突，知识库的踩坑汇总明确警告过这是整文件级的操作——事后核对这次两个分支只差一个断言的排版，没有丢内容。
