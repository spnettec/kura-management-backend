2026-11-17 修订。部署与持续配置必须提供界面入口；必需的环境变量编辑、`setup.py` 或容器重启命令不算界面交付。此文替代 2026-11-09 旧稿的实施步骤与 P1/P2/P3“已交付”标签，旧稿与各次有限验收可在 Git 历史及原检查点查阅。全部 12 父项继续由 [完整台账](checkpoints/20261116/OPEN-TASKS.md) 管理。

## 已核定方向

当前使用用户选择的**方案 A：外部签发，中心不默认保管 CA 私钥**。此前关于中心托管根钥、直接一键签发或等待再次选择 A/B 的表述不再是实施指令。组织 CA 服务可以提供自己的签发界面；本系统通过 CSR 下载、外部签回、公开证书上传和指纹核对接续。测试脚本是验收准备手段，不能成为最终用户必须操作的步骤。

- 装有 Kura 的网关由 Kura Java 后端生成并保管私钥/CSR；不依赖 agent 生成服务。原 GWT 仅在正式安装 agent 后显示远程管理入口。安装检测、agent 活性、身份状态和中心可达性分别呈现。
- 独立 agent 需要网关本地身份/CSR 与证书导入界面，不能依靠尚未建立的中心通道完成首次配置。旧一次性身份包保留为明确选择的兼容入口，须说明其私钥交付范围，不把它当成本地 CSR 流程。
- 中心可为自身 TLS 生成服务器私钥和公开 CSR；CA 私钥留在外部。这与网关私钥、Kura 加密原钥、中心任务数据钥分别管理，不相互授予读取权。
- agent 平时常驻。远程开关只控制到中心的通道，不停止本机恢复；维护停机必须是单独、明确的操作。Kura 可以不装 agent 独立运行，不增加 agent 启动依赖。
- 默认能力关闭；本机 UID、固定暂存目录、允许接口、网络 writer 和远程通道分别授权。不能为了让向导通过而放宽 Root 文件配对或读取 Core 原钥。

## agent 的安装与维护顺序（R017）

安装器可能已经启动 agent，而旧 `import-identity`、导入包、CSR 和授权命令要求服务处于 inactive。不能直接在安装后调用这些命令，也不能修改 guard 来迁就顺序。

本机界面需要先显示身份/远程决定、正在处理的请求、执行库和各事务的未决状态；只有审查通过后，才允许用户明确进入维护。持久原意图先于停机/材料写入。完整操作应为：审查 → 明确维护停机 → 核定 inactive/PID0 → 原材料校验/导入或授权 → 检查 → 单独明确激活。失败保留原意图和材料，不隐藏重试、自动换号、删除标记或默认关闭恢复。已受理的 UNKNOWN 不得按“当前 inactive”推断成功。

对于已有 Kura 的首次身份接收，优先使用常驻 agent 的 `remote.bind` 合同；Kura 生成私钥，agent 独立复制/校验并保留原回执，接收后仍为远程 OFF。这条数据路径不能代替 OS 本机授权界面。旧 CLI 仅作为管理员后备；示例中的显式停机也不算 R017 产品界面完成。

## 组织 CA 保管与审批

[组织 CA 保管审查](provisioning-ui-security-review.md) 的威胁分析与建议继续保留，但不把其中可选 B 方案自动转成当前选择。需要落实多个具名管理员、独立外部签发职责、人员不可用时的组织恢复与高影响变更的多人审批。单人持有测试 CA 或一个主机 Root 账号不能冒充已实现多人 custody/quorum；应用审批也不能证明能抵抗同时控制主机、数据库和解密材料的人。

## 所有入口共同的准入和回执

- Web 身份、设备 mTLS 身份、OS 管理权限和密钥服务权限独立。管理写继续验证 ADMIN、Origin/CSRF、首改密码和既有审计合同；首改完成前拒绝其他管理 API。
- 私钥不进入公开 DOM、日志、配置快照或任务结果；公开 CSR、证书链、摘要和到期时间可以展示。下载包或外部材料只按已核定的专用生命周期交付。
- 在提交前保存原申请/操作身份和材料摘要；失败后冻结相关写按钮，只读核对同一 Root 的原权威记录。监听、PID、文件出现或已换证均不能替代原结果回执。
- 原三现场、个人配置/密钥/数据、运行中 target/runtime 及所有未决材料保留。已闭环的备份、归档、轮换、恢复和 900 秒续期验收不重放。
- 完整 Core/networking/GWT/agent/console/Docker、provider/launcher/模式、安装升级移除、协议发布与联合代次继续内部 pending。external deferred 仅原三项：实际 NM/cloud-init/物理硬件、amd64、磁盘满/硬断电。
