## 为什么做这么长

1. **验证粒度与工程价值不成比例**。每个微操作（如一次快照格式转换）都要在 ARM64 独立夹具里走完整生命周期（安装→暂存→准备→启动→CM 应用→停止→发布→受保护启动→健康→停放），每步存 JSON 证据。一个场景产 30+ 文件、占 2GB+、耗数小时。这些验证对发现真实 bug 有价值（如 historical-snapshot 密码明文、CM 存储重建等），但对已经稳定的路径是重复劳动。

2. **组合爆炸**。每类操作（安装/升级/移除/purge）× 每个中断点（SIGTERM/重启/回执丢失/回执后中断）× 每种凭据状态（单钥/多代/UNKNOWN）都要单独验证。理论组合数百个，实际做了不到 80 个，没有一个父项因此关闭。

3. **每轮产生新 deb（205MB）**。每轮 Core WIP 提交后重建 deb 用于夹具验证，旧 deb 留在 target 目录。数十个 deb 占 22.7GB。

4. **没有父项级收口机制**。每轮结束只记检查点和台账，从不评估"这个父项的所有子项是否已覆盖，能否关闭"。结果：证据持续积累，父项永远开着。

## 过度设计的具体表现

- **D 场景做了 5 次尝试**才成功——前 4 次因宿主内存不足反复失败，每次都是完整夹具重跑。实际只需要一次成功验证。
- **C 场景发现结构性不可达**后仍尝试了多次全链——实际上结构发现本身就是结论（转换上限=恢复备份上限），不需要强行走通。
- **相同的中断恢复模式**（SIGTERM→原号续办→补回执）在快照发布、包维护、密钥轮换、provider 重加密等至少 10 个场景中重复验证，每次都是新夹具新 deb 新证据。

## 当前设计（一句话版本）

Rust/React 中心（kura-management-console）+ 可独立运行的 Core/GWT + 可选常驻 agent + 保留 NetworkManager。核心改造在 Core WIP 中：快照导入转换、CM 受控恢复、密钥生命周期、包生命周期（install/upgrade/remove/purge）、typed brokers（RTC/Chrony/Reboot等）、原生 agent 委托。这些都已有代码和定向测试，缺的是**正式发行**和**父项级验收收口**。

## 降粒度原则

1. **单元+定向测试已覆盖的路径不再做 ARM64 全链**——只在最终发行验收时跑一次全链。
2. **同一模式不同参数不再重复验证**——SIGTERM 中断恢复已在 10+ 场景验证，新场景只验参数差异。
3. **每个父项一条关闭结论**——不再产出几十个中间 JSON，只留一个"已验证范围+关闭结论"文档。
4. **磁盘控制**——每关闭一个父项，归档其阶段目录为 tar.gz，删除原目录。
