## 已复现的 P1：续期会占满原启动需要的容量

两个全新、独立 Linux 模型使用产品 Root/准入/真实密码 JAR 和持久文件；
Core/systemd 明确为模型。它们没有访问正在进行的实际安装场景或原保留网关。

| 边界 | 续期前 | 当前行为 | 随后的原启动 |
| --- | --- | --- | --- |
| Root 共同准入 | 255 个已结算记录，原启动从未申请 | 续期获得最后一个准入，成功写入原生续期回执；共同准入达到 256 | 原启动在预留时得到 `CAPACITY`，没有原启动原生记录 |
| Root 原生操作 | 255 个已成功操作，共同准入有空位 | 续期成功占用第 256 个原生记录 | 原启动先被共同准入写为 `INTAKE`，随后 `journal_admission()` 拒绝 `CAPACITY`；没有原生启动原件，成为不可重发的未决原启动 |

两种情况下均没有启动 Kura。第一种会耗尽后续授权入口，第二种还使固定原启动进入
`INTAKE`/缺原件。不能用换 ID、删除旧记录、扩大白名单或重放原启动来修复。
这属于内部产品缺项，不能归入磁盘满/硬断电的 external deferred。

复现方法：在配置了 repository/JDK21/cipher 的 `test_key_start_lease.StartLeaseTest`
新夹具中完成原发布并令该**模型**授权过期。分别填充 255 个合法签名、已结算的
共同准入，或把合法成功原生操作填至 255；随后通过产品 `SenderAdmissions.reserve/execute`
完成一次 `start-renew`，再申请原固定 `startOperationId`。实际安装场景仍按真实
900 秒验证；模型中的时钟调整不构成实际过期证明。

直接根因：

- `SenderAdmissions.reserve()` 只对本次记录检查 `<256`，没有为已签发固定流程保留后续准入名额。
- `Manager.journal_admission()` 只对本次原生操作检查 `<MAX_OPERATIONS`，`MAX_OPERATIONS=256`。
- `Handoffs.renewal_preflight()/renew_start()` 核对了原发布、原写者、密钥代、cohort、boot、锁及原启动严格缺失，未核对启动容量。
- 启动的原生容量检查发生于共同 `INTAKE` 之后。界面隐藏续期按钮不能替代服务端原子门禁。

## 修复顺序与约束

先保证已签发流程能够使用原固定编号完成，再实施归档释放容量。
需要在共同准入锁内计算 Root 原生与发送方两种预算，并覆盖所有会消耗它们的入口。
仅在续期处多检查一次当前空位会被其他写入消耗，不足以解决问题。

固定发布/启动的容量承诺须绑定原授权。已保存、尚未物化的签发预留，也须保留其
后续容量；不能在 Root 先预留、GWT 保存私有意图的间隙丢失承诺。
正面完成或原撤销证明才能释放，超时、未知、缺原件或普通失败不能释放。
容量承诺与实际密钥发送预留应分开：不能提前制造原启动的实际预留，否则会违反
“原首次启动从未申请”以及旧编号永久关闭的规则。

至少验证：两个 255 边界的失败前置、原固定启动仍可完成、无关写入不能抢占承诺、
多个发送方及签发中断、原撤销/完成后的释放、重复/损坏/异命名空间及升级读取。
拒绝时须保留原意图和编号；不得把已存在的 `INTAKE` 改判成未发送。

GWT `GatewayKeyHandoffJournal.requireSettled()` 接受原 `GRANT_RECORDED` 或
`GRANT_REVOKED`，含义是原签发已确认；不能从中推断发布、启动或应用就绪。
恢复端 `completed.json` 是原请求回执的本地确认，不是 Root 的归档证明，也不是
全部 provider 就绪证明。

## 归档必须保留的读取与禁止重发语义

- 原授权、全部固定 ID、原操作/预留、原请求 tag 与正面结果保持可核对。
  不能删除后把“缺失”当作全新请求；迟到原帧必须继续拒绝。
- Root 自己验证原发布及原启动成功、匹配授权和命名空间；`SYSTEMD_JOB_ACCEPTED`
  仍只表示请求回执，不改称应用就绪。历史授权不能要求旧 Core PID 仍存活。
- 现用代的普通启动门禁仍要读取原发布/启动记录。归档不能使
  `Generations.current()/require_start()` 找不到它们。
- 三类 GWT 和独立恢复的私有字节由各自 UID 处置。Root 不能获得读取两方私有目录的能力。
- 归档部分完成时保留原编号、可查询的持久意图和原件；查询不替用户完成移动，
  只能按原认证凭据继续尚未完成的固定元数据步骤。
- 所有包读取、重配置、初始化、升级/卸载、版本/cohort 和旧客户端都需明确配对。
  不能只给新目录加白名单或仅增加最大计数。
